# Browser player mappings and touch-overlay editor

Status: approved by the user on 2026-10-30, including the interactive layout mockup. The options/shader batch is committed as `4961594`. The user requested controller, keyboard and mouse mappings with an overlay editor, prioritizing Safari on Mac and iPhone, and explicitly chose playable touch controls for this batch.

## Intent and approach

Keep our Svelte player and opaque sandbox. Give people one understandable mapping from their keyboard, mouse buttons, connected controller or touch controls to a logical RetroPad. Provide a live reference diagram and an editable on-screen layout. Preserve native mouse/keyboard passthrough as an explicit mode for cores that need it; do not pretend RetroPad mappings implement an emulated computer keyboard, mouse, lightgun or device-port adapter.

The recommended approach is an owned web mapping/editor UI with a bounded guest-side virtual-gamepad adapter. It reuses the existing native Emscripten gamepad polling path, without sending gameplay edges through the anonymous save/settings command queue. User-visible design decisions below are proposals, not additional requirements attributed to the user.

Alternatives considered:

1. **Recommended:** our web editor and virtual-pad adapter. Live changes, independent input timing and ordinary DOM controls; requires explicit per-build acceptance of the gamepad driver and mapping configuration.
2. Generate native RetroArch overlay/config files and reload settings. Useful future import/export compatibility, but does not itself give our editor a reliable live binding, device discovery or reload-completion contract. Broad config reload is a poor default while a game and pending saves are active.
3. Send `SET_INPUT` commands for gameplay. The pinned frontend exposes them, but their replies share the same native queue as saves/settings. Per-edge commands would require a new native reply multiplexer or a new core ABI; do not add that coupling for this batch.

## Evidence and platform limits

A throwaway probe on 2026-10-30 supplied a standard-shaped virtual controller to the sandbox's own `navigator.getGamepads`, emitted its connection event and configured the pinned FCEUmm build's `rwebpad` bindings. Pressing/releasing its A input changed the original generated program's battery counter from 1 to 2, then left it at 2 after release. Desktop WebKit and iPhone-profile WebKit both passed. This verifies a programmatic virtual-pad path for one build, not real multitouch, hardware-controller pairing, mouse behavior, latency or installed Safari acceptance. Probe code and generated bytes stay outside the repository at `~/.cache/ecs-nostalgist-spike-20261028/input-virtual-probe.mjs`.

Physical controller exposure still obeys browser policy, secure-context rules and user interaction. Do not equate an empty browser device list with no controller connected; explain pressing a button to reveal a device, and report unavailable/denied access separately. Virtual touch/keyboard input does not create access to hardware hidden by browser policy. No WebHID requirement or Safari experimental-feature toggle for ordinary controls.

## Input engine and boundary

- Capture real keyboard/mouse gameplay events and read physical gamepad snapshots inside the guest. Save the native gamepad getter before installing the guest-only adapter. Never replace host-page APIs or browser permissions. Give the native driver bounded, standard-shaped virtual pads representing up to four player ports, with explicit RetroPad button/axis bindings. Keep physical browser device indices separate from emulated port numbers.
- First gate the adapter to the tested RetroArch/gamepad-driver path; new builds require actual acceptance. Unsupported/custom runtimes keep their existing native input and show mapping/touch functionality unavailable. Do not disable working native input before the adapter is ready. Startup/config failure must not silently leave a game unplayable.
- Keep keyboard, mouse, physical-pad and touch contributions separate. Releasing one source must not release an action another source still holds. Clamp finite analog values; apply per-device dead zones and inversion. Resolve opposite digital directions to neutral by default. Define deterministic analog-source arbitration and test it.
- Keyboard bindings use physical `KeyboardEvent.code` with a readable label, not an assumed US character layout. Capture only when explicitly binding or playing in the focused game. Ignore composition, modifier-only keys and editable host fields. Preserve browser navigation/shortcuts; reject reserved combinations. Cancel binding with Escape and require a new neutral-to-active edge for capture, rather than binding a button already held when capture starts.
- In pad-mapping mode, suppress duplicate native pad keyboard bindings and unsafe default frontend hotkeys. Native save/load/reset/quit hotkeys must not bypass our save completion and upload controls. Borrow Nostalgist's hotkey-disable pattern as a reference, retaining attribution if source is copied. Keyboard passthrough is explicit; do not globally suppress ordinary typing or browser shortcuts.
- Mouse mode defaults to native pointer passthrough. Optional pad mappings cover mouse buttons and wheel pulses with clear labels. A wheel pulse must release after a bounded core frame interval. Native pointer movement remains the core's existing path; mouse-movement-to-stick conversion and its sensitivity editor are follow-ups. Axis dead-zone/inversion controls apply to controller/touch sticks in this batch. No claim that every core supports mouse/lightgun input. Do not enable pointer lock or change sandbox/policy in this batch.
- Touch DOM controls live in the trusted host player stage and feed bounded logical source state through a dedicated realtime message path. This path cannot wait behind filesystem, screenshot, shader or save RPC work. It accepts only validated input snapshots/releases and bounded layout/status messages, never arbitrary native functions or commands. Coalesce redundant snapshots, preserve quick-tap press/release edges across at least one native input poll, bound queued work and use a watchdog so an abandoned host cannot leave buttons held.
- Keep gamepad sampling local to the guest/core polling cadence. Send only bounded device summaries, binding-capture results and low-rate live highlights back to the editor; do not stream every frame to Svelte or enumerate devices in the core's save reply channel.
- Treat the host stage and guest canvas as one player region. Host touch controls retain gameplay ownership while the top-level document is visible/focused; moving focus between the host controls and guest is not a global focus loss. The host supplies the guest's bounded active/inactive state with a watchdog. An iframe blur releases that iframe's keyboard/mouse contribution only, not a touch or physical-pad source owned by the active stage. Verify top-level document focus, including a focused descendant iframe, before treating a window blur as leaving the app.
- Release affected input on pointer up/cancel/lost capture, controller disconnect, binding/editor entry, mode/map changes, page hiding, actual top-level focus loss, teardown and transport loss. After returning from a hidden/unfocused document, require neutral/new interaction before rearming held controls. A visible Release all controls action is always available. No automatic game restart.
- Keep focus on host controls while pointers are held, rebinding or editing. After the last touch releases in play mode, keyboard focus may return to the guest only if the player still owns focus and no editable host field is active. Provide an explicit Back to game action. Never steal focus from a field or cancel active pointer capture merely to focus the iframe.

## Mapping controls

- A controller diagram shows logical action labels, current keyboard/mouse/controller bindings and live pressed highlights. Standard gamepads use standard positions; unknown layouts use raw button/axis numbers. Do not invent brand-specific names or core-reported action labels that the runtime does not supply.
- Choose the player port, assign a discovered device, then select an action and press a key/button, move an axis or click the chosen mouse button. Offer clear/unbind, restore built-in mappings, axis dead-zone/inversion and a live test area. Device capture must not also press the game. Show duplicate/conflicting bindings before applying rather than silently taking a binding from another action.
- One physical pad belongs to one port at a time. Keyboard/mouse/touch can supplement the selected port. Persist reusable model/shape mappings without treating a browser connection index as identity. Ambiguous identical controllers require explicit assignment after reconnect. A core may need its own multiplayer/multitap options; four virtual ports do not prove four-player support for every core.
- Apply mapping/layout changes atomically after releasing affected source state. Mapping edits are session-only until explicitly remembered. Applying does not reload the core, reload its whole config or consume save replies. Pending save uploads must remain retryable/exportable; releases must always work even while other controls are busy.

## Touch surface and layout editing

- Provide a compact two-button layout and a standard RetroPad layout made from original shapes/text. D-pad, face buttons, Start/Select, optional shoulders/triggers and a virtual analog stick are available without copyrighted controller artwork. Keep logical RetroPad labels unless verified core descriptors become available.
- Support a translucent overlay and an underlay that reserves space around/below the game. Portrait and landscape layouts are separate, with safe areas, normalized positions and resize/scaling support. Fullscreen must include controls where supported; ordinary embedded play remains usable on iPhone without fullscreen.
- Play mode supports multiple simultaneous pointers, direction+button combinations, dragging a thumb across a D-pad, and an analog stick returning to neutral on release/cancel. Prevent browser scroll/zoom only within active touch hit regions; the rest of the page remains navigable. Controller/keyboard use can hide touch controls without removing their saved layout.
- Edit mode releases gameplay controls and uses drag/resize handles instead of sending input. Show selected control, action, position, size and opacity, with numeric fields/step buttons so editing works without precision dragging. Add/remove controls, restore a preset, undo the current edit, apply/cancel and a clear Done action. Rebinding selects a logical action, not an arbitrary native command or application shortcut.
- This batch suspends mapped input during editing; it does not add a native pause/resume contract. Clearly tell the user the game continues before entering edit mode, and keep existing save/export controls accessible. Do not silently unpause a core whose prior pause state cannot be established.
- Bound control count, label lengths, normalized geometry, opacity, hit areas and layout JSON. Keep controls within the usable region after rotation/resize; never allow an invisible or oversized control to intercept the whole app. The editor's escape/Done and Release all actions must remain reachable outside the editable hit regions.
- Reference mode is noninteractive and shows bindings/highlights; play mode handles touch; edit mode handles layout. Mode switches are explicit. Screenshots keep game/shader pixels; the host touch interface is presentation, not part of native state thumbnails or captures.

## Remembered settings and recovery

- Separate versioned input preferences from core-options/shader preferences. Scope by browser/server origin and exact core build, with per-core defaults and explicit per-game overrides. Retain separate portrait/landscape layouts. Remember only edited keys for the chosen scope so inherited core bindings do not become accidental game overrides.
- Store only validated mapping/layout data and a bounded device model descriptor. No tokens, raw event history, arbitrary HTML/SVG/scripts, browser connection indices, game bytes or saves. Private/unavailable/corrupt local storage leaves playback usable with defaults and a useful warning.
- Clear/reset changes future defaults or explicit session settings as labeled; do not erase other scopes or restart the game. Failed adapter setup retains existing native input and does not overwrite remembered mappings. Failed edits keep the prior applied map/layout; unknown transport state releases controls and requires reload where safe recovery cannot be established.

## Validation and boundaries

Changes stay in `apps/web` and relevant documentation. Keep the opaque `allow-scripts` sandbox, existing CSP and credential boundary. No native/core rebuild, new package, server/API/schema change, pointer-lock permission, MIDI/HID/gyro support, macros/turbo or native overlay-pack import/export in this batch.

Use meaningful test-first regressions for validation/injection, source aggregation, short taps, axes/dead zones, capture-neutral gating, disconnect/blur/hidden releases, watchdogs, port assignment, atomic map/layout updates, preferences and scope isolation. Test actual editor gestures and touch cancellation, portrait/landscape, underlay/overlay, visible highlights, pending save coexistence and keyboard typing outside the game. Native input/saves/settings must remain independently ordered.

Real-core acceptance uses the original generated NES program: remapped keyboard/mouse-button/virtual-controller/touch presses change game data, releases stop changes, simultaneous touch works, and saves/screenshots/shaders still function. Prioritize desktop and iPhone-profile WebKit, plus Chromium. Synthetic gamepad snapshots prove adapter behavior, not hardware pairing; physical Mac Safari/iPhone/controller acceptance and sustained performance remain explicit gaps unless directly tested. Run affected web tests, Svelte check/build and one focused review of the realtime bridge, lifecycle and storage risks. No full core/native/OS matrix.

Builder discretion: exact limits/deadlines, component names, lightweight drawing style and deterministic axis arbitration, settled from tests and recorded. If the verified virtual driver cannot support live remaps reliably, return to the adapter choice before replacing it with a new native ABI or claiming partial input support.

The builder check identified the host-touch/iframe-focus ambiguity. The ownership and refocus rules above resolve it; there are no remaining consequential unanswered builder questions. The user approved implementation, then asked to correct preview spacing and evaluate Delta skins before proceeding. The corrected mockup uses equal edge insets and equal face-button sizes without CSS overriding the inspector's size values.
