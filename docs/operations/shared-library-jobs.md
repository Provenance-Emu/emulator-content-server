# Shared library work

Use **Library tools → Library activity** to match existing indexed games or scan saved folders. Jobs belong to the server and appear across signed-in owner sessions. Closing a tab or signing out leaves the job running. Cancel from any owner session; resume processes pending work. Failed and unmatched retries reuse the job. Review acknowledgements persist without silently saving suggestions.

SQLite stores job scope/options, a keyset work list, outcomes and aggregate progress. Duplicate active scopes/options reuse a job; partial overlaps with different options return conflict. One worker services bounded pages of 50 sources and yields between files. The UI requests 20 outcomes at a time and pages older activity; a selected job remains visible and refreshed when newer jobs move it out of the first history page. Old per-tab bulk execution is no longer used by the library. Legacy scan calls and enabled watchers enter the same worker.

A restart marks an active job interrupted, retaining completed outcomes for explicit resume. Queued jobs start on readiness. Cancellation cannot publish a partial folder traversal as evidence that files disappeared. Existing saved metadata/artwork, files, sessions and root assignments survive migration. The worker reloads the creator's current permissions. Job inspection/control/review endpoints require the server owner.

Matching never overwrites an occupied category. Automatic saving still requires one unambiguous checksum candidate per category, agreeing systems and healthy providers. Filename-only matches, ambiguity and provider failures remain reviewable. One exact canonical box cover can be corroborated by a ROM checksum identity, including compatible legacy/regional title aliases from independent catalogs; ambiguous covers, alternate editions, title screens and screenshots remain reviewable. This is game identity evidence, not a checksum equality claim about image bytes. Unlisted games cannot acquire fabricated details.

## Resource behavior

- Folder availability is freshly checked; local-volume probes avoid per-file subprocesses, and other mount-type facts are cached briefly by device. macOS mount types and Linux filesystem mode are read correctly for network-volume classification.
- Folder enumeration streams directory entries. Metadata I/O batches are limited to four on internal volumes, two on network volumes, and one on removable/iCloud volumes. ROM bytes and cloud placeholders are not opened by enumeration; only bounded local disc descriptors are parsed.
- Companion lookup uses persisted normalized directory/stem/extension indexes, including legacy rows. Each indexed seek and combined result are bounded. It does not reload a folder's entire source list for every game.
- Healthy OS watchers use a 15-minute full audit for missed-event recovery; the 30-second poll checks root identity and unavailable watchers without repeatedly walking an unchanged healthy tree. Fallback scans back off according to scan duration (30 seconds to five minutes). Filesystem events still trigger debounced scans.
- Hashing uses 64 KiB chunks, a 64 MiB ROM ceiling, cancellation, and before/after identity/size/nanosecond timestamp checks. SQLite caches hashes against a fresh source ETag including identity and timestamps. Changes invalidate reuse; container hashes are not inner-ROM identities. ZIPs can hash exactly one eligible raw ROM using bounded stored/DEFLATE streaming and no extraction. Container and expanded bytes are each limited to 64 MiB, directory metadata to 1 MiB, entries to 256, compression ratio to 100:1, and elapsed time to ten seconds. Inner CRC/length and outer identity are checked; encrypted, symlink, ambiguous, nested, unsupported and disc-layout archives stay filename hints. A versioned cache separates inner ZIP hashes from raw-file hashes. A CRC-only catalog remains usable when the source also has MD5; an explicit conflicting catalog MD5 is never downgraded to CRC evidence. 7z and CHD inner-content matching remains deferred.
- Providers run in isolated child processes with bounded messages, memory and deadlines. Public catalog caching is separate from ROM checksum caching. The host reuses at most two serial workers, with a 64-request queue, 192 MiB heap cap, per-request deadline, five-second idle expiry and periodic recycling. Parsed/indexed public data is bounded (32 MiB raw cache plus 64 MiB parsed/index estimate, at most eight parsed datasets). Cancellation or timeout kills the active child before replacement. No provider code runs in the HTTP process or browser.
- Progress uses stored aggregates. Result listing uses indexed state/keyset seeks; it does not repeatedly count or scan 100,000 completed rows to find the next pending page.

## Generated benchmark

`node scripts/benchmark-matching-index.mjs 100000` creates a temporary generated catalog, performs 1,000 companion lookups, records query plans and removes its data. It never reads an operator catalog or ROM bytes.

The 2026-10-28 run indexed 100,000 generated ROM records plus 500 sidecars in about 3.35 seconds. After eliminating SQLite's whole-root ORDER BY plan, 1,000 lookups took about 254 ms total, with p95 about 0.26 ms. The initial indexed-but-unconstrained plan took about 48 seconds for the same lookups. These are local database measurements, not end-to-end matching throughput or disk/network speed claims. Filesystem inspection retains an O(n) snapshot for conservative rename/absence verification; streaming transactional scan staging remains a later memory optimization.

Regression coverage includes a pre-queue catalog retaining saved choices across two reopens, normalized sidecars beyond 50,000 entries, a 60,000-completed-row queue index plan, cross-session cancellation, disconnected HTTP requests, resume/retry and persisted review. Manual provider choices and source revision checks remain authoritative.

The existing 16 MiB public-catalog body bound remains. An oversized upstream dataset needs a split or streaming index adapter; raising concurrency or creating more browser sessions does not bypass that bound.


## Existing-library acceptance — 2026-10-28

The operator's existing 1,608 indexed source rows, two root assignments, one user and two sessions survived the schema upgrade and subsequent detached server updates. The initial pre-feature catalog had 13 metadata choices and one artwork choice. A shared 935-game pass added 29 safe metadata selections in 15.636 seconds. Explicit `[BIOS]` filenames were then correctly classified as firmware, reducing Games by 17 entries without changing or deleting source files.

After bounded ZIP support, CRC-only catalog lookup and compatible checksum-title aliases were corrected, a shared pass completed all 918 game entries in 13.991 seconds with zero failures and added 82 Jaguar artwork selections. Final coverage is 42 metadata selections and 83 artwork selections. All 43 choices present before the ZIP follow-up remained byte-for-byte intact; new art was downloaded through the normal bounded provider bridge. SQLite integrity passed, and the installed Mac app rendered the newly saved covers.

These timings describe this local, warm catalog, including the selected provider/cache state; they do not predict throughput on 100,000 disc images or a slow remote volume. The final job retained 570 review outcomes and 333 unmatched outcomes. 7z/CHD inner-content fingerprints, unsupported archive layouts and broader automatic Dreamcast/arcade coverage remain follow-ups. Filename hints are available without pretending they are checksum verification. The released 0.1.6 installers remain frozen; the later matching fixes are on main and active in the local service, and the browser UI additionally has paged job history.


## Identification and review policy

ROM identification now runs through offline plugins in the isolated worker, including bounded 7z inner-ROM hashing, CHD header facts and supported bounded disc-ID reads. Facts are cached against source identity and reader/tool configuration. Hash, serial and catalog evidence reconcile before automatic selection; compatible multi-source aliases no longer count as separate games. See [identification plugins](rom-identification-plugins.md).

New web jobs expose **For new jobs, use exact filenames when a game ID is unavailable**. The UI enables this explicit fallback by default; the v1 API remains verified-only unless `allowExactNames:true` is sent. Fallback requires the full title/edition or catalog ROM filename to agree, an explicit catalog system to agree with the source system, and no stronger hash/serial/size/release conflict. It retains `name` confidence and an `exact-name` label. It does not promote partial/fuzzy/local-sidecar suggestions or a differently named cover through an unverified set alias. A job's policy persists and is shown to other sessions.

Optional back/disc/manual/title/screenshot suggestions no longer make a game with saved primary choices appear conflicted. They remain available under **Saved → Review** and the game's matching panel. A genuine missing primary choice, conflicting candidate, provider problem or unavailable selected resource remains reviewable. Resource download failures retain selections already committed for the game, rather than losing their saved count or repeatedly downloading the same unavailable image.
